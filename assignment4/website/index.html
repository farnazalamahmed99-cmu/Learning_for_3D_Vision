1. Multi-View Data Preprocessing (20 points)

Each training sample is built from 8 views of one ScanNet++ scene. Each view is a 400×300 RGB image with depth. It is center-cropped to 300×300 and resized to 224×224 (Q1.1). The depth is unprojected to 3D points (Q1.2). Everything is expressed in the first camera's frame and normalized in scale (Q1.3). Finally, a ray (Q1.4) and its Plücker coordinates (Q1.5) are computed for every pixel.

1.2 Depth unprojection (original world frame, meters)

Each pixel \((u, v)\) with z-depth \(Z\) is unprojected as \(\mathbf{X}_\text{world} = R\,(Z\,K^{-1}[u, v, 1]^\top) + \mathbf{t}\), using the resized intrinsics and the camera-to-world pose. Points from all 8 views fuse into a single consistent scene, and each camera frustum sits where its view was captured.

1.3 Canonicalized geometry (first-camera frame, normalized units)

After canonicalization, camera 0 is the identity, so its center is at the origin. The valid-point centroid lies exactly 1 unit from it. Explanations

Canonicalization

Raw ScanNet++ poses live in an arbitrary per-scan world frame, and each room has its own physical size. A model would otherwise have to infer an absolute position and scale it cannot observe. Canonicalization removes both. First, every camera-to-world pose is re-expressed relative to the first sampled camera: \(T'_i = T_0^{-1}\,T_i\), computed in float64. This makes camera 0 the identity, at the origin and looking down \(+Z\). Depth is then unprojected in this frame, and the valid-point centroid distance \(s = \lVert \operatorname{mean}(\mathbf{p}_\text{valid}) \rVert\) is computed. Translations, depth and points are all divided by \(s\), and rotations are left unchanged. The centroid is not subtracted, so camera 0 stays at the origin and the scene's centroid sits exactly 1 unit away. Every training sample therefore shares the same reference frame and scale.

World-space ray directions

For pixel \((u, v)\), \(K^{-1}[u, v, 1]^\top\) gives the viewing direction in camera coordinates, with \(z = 1\). Rotating it by the camera-to-world rotation and normalizing gives the world-space unit direction \(\mathbf{d} = \dfrac{R\,K^{-1}[u, v, 1]^\top}{\lVert R\,K^{-1}[u, v, 1]^\top \rVert}\). Only the rotation is applied: a direction says which way the pixel looks, not where the camera is. The ray origin \(\mathbf{o}\) is the camera center \(\mathbf{t}\), shared by every pixel of that view. Every surface point seen by the pixel lies on \(\mathbf{o} + \lambda\mathbf{d}\), \(\lambda \ge 0\). This is what the ray reprojection check verifies.

Plücker moment

The Plücker coordinates of a ray are \([\mathbf{d}, \mathbf{m}]\) with moment \(\mathbf{m} = \mathbf{o} \times \mathbf{d}\). The moment does not depend on which point of the line is used as the origin: \((\mathbf{o} + \lambda\mathbf{d}) \times \mathbf{d} = \mathbf{o} \times \mathbf{d}\), because \(\mathbf{d} \times \mathbf{d} = 0\). So the 6-vector describes the line itself, not one point on it. Geometrically, \(\mathbf{m}\) is normal to the plane containing the ray and the origin, and with unit \(\mathbf{d}\), \(\lVert \mathbf{m} \rVert\) is the ray's perpendicular distance from the origin. Camera 0 sits at the canonical origin, so all of its rays have \(\mathbf{m} = 0\). Other cameras' moments encode where they are relative to camera 0. This dense 6-channel map is the camera conditioning used by the models in Parts 2 and 3.

2. Novel-View Synthesis with Mini-LVSM (40 points)

2.1 Overfitting one batch

The model was trained for 2000 steps on a single fixed training batch, with the same model and optimizer settings as 2.2. It reached a final PSNR of 30.99 dB (SSIM 0.872, MSE 8.5 × 10⁻⁴) on that batch, which passes the ~30 dB sanity check. The averaged training PSNR over all 2000 steps was 25.40 dB (it starts near 12 dB). The run took 717 s on an NVIDIA A10G.

Discussion

Number of source views. With correct rays, quality improves steadily with more source views: 15.19 → 16.13 → 16.89 dB, although the model was trained only with 2. More views cover more of the scene, so less of the target has to be guessed. The model can use them because attention takes any number of source tokens, and the Plücker rays tell it where each source pixel sits relative to the target camera. The gain shrinks per added view (+0.94 dB, then +0.76 dB for two more), as views increasingly overlap.

Ray conditioning. The target rays are the only information about which view to render. With all-zero rays, PSNR falls to about 12.5 dB for every source count, and adding views no longer helps. The model then outputs a blurry average-looking image, which minimizes MSE when the viewpoint is unknown. Shuffled rays are worse still (about 11.5 dB, lowest SSIM). The model trusts the rays and renders a confident but wrong viewpoint, and a sharp wrong image costs more MSE than a blurry average one. Together these show that the model really does use the camera geometry, rather than memorizing scene appearance.

Limitations. Predictions are blurry and show 8×8 patch seams. Small model, 100 epochs on 224 clips, and the MSE loss all favor smooth averages of plausible outputs. Regions not visible in any source view cannot be recovered and come out as a smooth guess.

Results. The two models are nearly identical. The validation curves overlap throughout training. The largest difference is +0.12 dB at S = 4, the setting the baseline never trained on, and S = 1 is unchanged. SSIM differs by under 0.01 everywhere, and the shuffled/no-ray settings are unchanged; the images are visually indistinguishable.

Interpretation. Training with varying S gives at most a small benefit for more views than trained with, and nothing for fewer. The baseline already generalizes across view counts. The small model is capacity-limited (~16 dB), and that bottleneck dominates any effect of the view-count curriculum.

Limitations. One seed per configuration. Differences of ~0.1 dB are likely within run-to-run noise, so the S = 4 gain is only suggestive. A firmer answer needs several seeds, longer training, a larger model, and harder settings (for example, S up to 7 or wider baselines), where a fixed-S model might generalize less well.

Discussion of errors on held-out scenes

What works. On unseen rooms the model recovers the overall scene layout and scale. Floors, walls, the hallway and the desk area are in the right places, and the valid-point centroid distance of the predictions is 0.97–0.99 (GT: 1.00), so the predicted metric scale is nearly correct. Depth is good at the coarse level (δ1 ≈ 0.80–0.83, AbsRel ≈ 0.14–0.15), and relative rotations are mostly within 15–30° (rotation AUC@30 ≈ 0.71). Val and test are close, so the model generalizes consistently to new scenes.

Depth errors. Predicted depth is over-smoothed. Thin structures disappear (the chair legs and table edges in 09c1414f1b), depth discontinuities are blurred into ramps, and flat walls become slightly wavy and thick in 3D. The depth head decodes each 14×14 DINO patch with a linear layer plus a tiny convolutional refinement, so it cannot represent detail finer than a patch. The L1-style loss also favors smooth averages where it is uncertain.

Camera errors. Translation direction is the weakest output (AUC@30 ≈ 0.19, mean error ~41°), and it drags down the joint pose AUC. Views come from at most 32 consecutive video frames, so baselines are short and often dominated by rotation. For a short baseline, a small absolute error in translation becomes a large error in its direction. The model also has to infer translation purely from parallax in frozen DINO features, without iterative refinement. Rotation is easier: it follows directly from how image content shifts between views. Fine accuracy is low everywhere (AUC@5 ≤ 0.22), so the model gets cameras roughly right but not precisely.

Limitations. A small model (width 384) trained only on 224 clips for ~9 h on one A10G. The camera loss was still decreasing at the end of training, so longer training would likely improve poses further. Larger gains would probably come from a stronger depth decoder (for example, DPT-style multi-scale features), iterative camera refinement, more training data, or unfreezing DINO.

3.3 Bonus: how does the number of input views affect accuracy, runtime and memory?

Question. Mini-VGGT was trained only with 8 views, but its architecture accepts any number of views: frame attention is per view, and global attention simply sees a longer sequence. Does the trained model get better with more views (more parallax and more context), worse with fewer, or does it break outside its training setting? And how do runtime and memory scale?

Setup. Evaluation only, with the 3.2 checkpoint (best.pt, epoch 890) and no retraining. Full val and test splits, using the same protocol as 3.2 (first 32 prepared frames, 224 px, seed 825), with V ∈ {2, 4, 8, 12, 16, 24, 32}. The evaluation loader always takes frame 0 plus the first V−1 frames of a fixed per-scene random order. The view sets are therefore nested: every larger set contains the smaller ones, so V is the only thing that changes. As a check, V = 8 reproduces the 3.2 numbers exactly. Runtime and peak GPU memory were measured separately at batch size 1 on the A10G (bf16 autocast, 10 timed forward passes after warm-up; training step = forward + backward with frozen DINO).

Results and conclusions

More views do not help. Depth is best with the fewest views: val AbsRel goes 0.109 → 0.139 → 0.164 for 2 → 8 → 32 views, with the same trend on test. Rotation AUC@30 stays at 0.66–0.73 with no clear trend, and translation AUC@30 falls on val (0.28 → 0.17) and is flat on test. The model does not use the extra parallax. It does degrade gracefully, though: even at 32 views (4× its training setting) no metric collapses, because attention with per-view 2D positions works for any number of views.

Possible reasons (not verified): extra views dilute global attention in a way the model never saw in training; with few views, the easier reference view 0 makes up a larger share of the depth metric; and pose AUCs at small V use few pairs, so they are noisy.

Cost. Inference time is flat (~34 ms) up to 8 views, then grows faster than linearly: 52 ms at 16 views, 106 ms at 32. Inference memory barely changes (0.7 → 1.0 GB). Training memory grows linearly, about 0.1 GB per view, so 32 views at batch size 16 would need about 60 GB, more than the 24 GB GPU.

Limitations. One checkpoint, trained at 8 views and evaluated only. A model trained with more or varying views might benefit from them. All views come from the same 32-frame window, so extra views add denser coverage, not wider baselines.
